## delivery / critical

### F-01 — The determinism guarantee is broken by default: the CLI leaks the checkout directory name into output
- Topics: DEL-01.3, DEL-01 (business section)
- Evidence: The business promise is "output is byte-identical for the same sources and options on any machine" and the model crate's contract says "no ambient data... no absolute paths" (`crates/sealmap-model/src/lib.rs:33`-`34`). But the CLI, when `--name` is not given, names the codebase after the canonicalised checkout directory (`crates/sealmap/src/main.rs:393`, `main.rs:419`-`424`), and that name reaches the index and overview. CI's determinism checks pin `--name sealmap` (`.github/workflows/ci.yml:29`, `ci.yml:33`-`34`), so the tests cannot detect the default path's nondeterminism.
- Failure: Two agents or two machines clone the same tree into differently named directories and run `sealmap generate` with default flags; the index/overview bytes differ. Downstream caching by content hash misses or, worse, a diff flags "changes" that are only directory names, sending reviewers a false review pack; seal comparisons made under different names also diverge (`stale --since` reads the older tree under the current tree's name).
- Confidence: high
- Severity: high
- Marked by authors: yes (Tension, "determinism contract vs CLI")

### F-02 — The shipped seal gate misses roughly one in four real changes, yet remains a published command whose pass state reads as "current"
- Topics: DEL-02 (business), DEL-02.4, DEL-02.2
- Evidence: The CLI ships `resolve`, `stale`, `seal-check`, `verify`, `seal sign` (`crates/sealmap/src/main.rs:45`-`65`, published at 0.2.1, `Cargo.toml:6`), and the lifecycle marks a topic `Holds` when "ids resolve, sig and body match". The measured fact: "the per-symbol rule caught 0.76 of real staleness (`README.md:81`-`85`)" and "every staleness rule finer than per-file lost real changes" — which is why the surface was frozen (`docs/DESIGN.md:3`-`41`).
- Failure: An adopter runs `sealmap verify` as a staleness gate; `Holds` is read as "diagram is current", but ~24% of real code changes pass through uncited bodies. Agents consume stale diagrams believed verified. The defect is silent by construction — a miss produces a green gate.
- Confidence: high
- Severity: high
- Marked by authors: no (disclosed as an evidence-programme outcome, not flagged as a defect in the shipped surface)

### F-03 — The declared MSRV is false for every downstream consumer: published crates can pull `ignore` 0.4.30, which needs Rust 1.88
- Topics: DEL-01.2, DEL-01 (business), DEL-01.1
- Evidence: The workspace declares `rust-version 1.85` (`Cargo.toml:8`) and the business section promises "builds on a stated, tested minimum Rust (1.85)". The msrv job passes only because `Cargo.lock` pins `ignore` 0.4.29 (`Cargo.lock:290`) under `--locked` (`ci.yml:46`); the requirement is deliberately left at `0.4.23` (`Cargo.toml:35`), and 0.4.30 declares no `rust-version`, so "the resolver cannot avoid it" and it needs Rust 1.88 (`Cargo.toml:32`-`33`). A published crate ships without the lockfile.
- Failure: Any downstream project on Rust 1.85 depending on the published crates resolves `ignore` 0.4.30 and fails to build. The remedy is a manual pin each consumer must discover from a comment (`Cargo.toml:32`-`34`). The core adoption promise fails exactly for the audience it was made to.
- Confidence: high
- Severity: high
- Marked by authors: yes (Tension "MSRV vs dependency" and a Debt note)

### F-04 — "No environment" determinism likely has a second hole: the loader honours ignore files, which may reach outside the source tree

### F-08 — Review packs are not reproducible records: `--diff` compares a revision to the dirty working tree, not two named trees
- Topics: DEL-02.3, DEL-02 (business)
- Evidence: The business section calls the pack "one bounded, reproducible file". DEL-02.3 records that `pack` "was built to its own flags rather than the planned ones: `--diff REV` against the working tree instead of two named trees" (`docs/DESIGN.md:203`, `docs/DESIGN.md:213`-`222`).

Once the working tree changes, the exact artifact a reviewer saw cannot be regenerated from git history; two runs on two machines with different dirty states produce different packs (compounded by F-01 if `--name` is unset). - Confidence: medium — the flag semantics are stated; the irreproducibility follows from them
- Severity: medium
- Marked by authors: no

# Post-mortem: sealmap delivery surface

Basis: reconstructed from the delivery topics DEL-01 (verified at `cd7570b9`) and DEL-02 (verified at `eacc59ec`). Every `path:line` citation below is as given in that material; I have no other access to the code. Where I reason past the material I say so.

## Root causes, most likely first

### R-1 — A green `sealmap verify` was treated as "the diagrams are true", but the gate misses real changes by design and never checks most topics
- Topics: DEL-02 (For the business), DEL-02.4, DEL-02.6, DEL-01.1
- Chain of events:
  1. The operator adopts the seal workflow and runs `sealmap verify` as the gate on their corpus.
  2. Migration is one topic at a time, so most topics stay legacy `path:line`; legacy topics with no seal are "coverage only, never a failure" (`crates/sealmap-corpus/src/seal/check.rs:391`-`392`). In sealmap's own corpus at `ae478d9` this is fifteen of sixteen topics.
  3. The sealed minority passes when the cited signature and body match — "Holds means only that no cited body changed".
  4. A change of the kind the per-symbol rule misses — recall measured at 0.76 (`README.md:81`-`85`) — lands, or it lands in a legacy topic, or in an uncited part of a sealed topic's subject. `verify` stays green.
  5. The agent harness consumes the stale generated views and dense projection as current, acts on a misrepresentation of the code, and the wrong action reaches production data or a client system.
- Evidence: "every staleness rule finer than per-file lost real changes for at most about 2× fewer flags" (DEL-02, For the business); the per-symbol rule "caught 0.76 of real staleness" (`README.md:81`-`85`); the `Holds` caveat (DEL-02.4); legacy topics never fail (`check.rs:391`-`392`); the seal surface is frozen as experimental (`README.md:367`-`378`).
- Warning signs visible today: the measured miss rate is published in the README; the surface is frozen; the gate has never run green even on sealmap's own corpus (MER-02 fails it, `check.rs:390`) and no CI job runs `verify` (`.github/workflows/ci.yml:9`-`84`, DEL-01.1) — the gate's false-pass behaviour on a real corpus is unexercised outside fixtures.
- Confidence: high on every stated fact; the incident chain is inferred.
- Severity: high.

### R-2 — A review pack sent to an outside reviewer leaked source, because the diagrams-only `--review` mode was designed but never built
- Topics: DEL-02 (For the business), DEL-02.1, DEL-02.3
- Chain of events:
  1. A client requires external review of a codebase's documentation; the operator reaches for `sealmap pack`, reasonably believing the diagrams-only variant exists, because the authoritative layer table still lists it (`docs/DESIGN.md:84`).
  2. The built CLI has no such flag (`crates/sealmap/src/main.rs:45`-`65`); every pack the tool can produce contains "topics, dense slices, source windows" (`crates/sealmap-corpus/src/pack.rs:274`).
  3. The pack is generated with `--diff REV` against the *working tree* (DEL-02.3), so uncommitted local content can be included.
  4. The pack leaves the trust boundary with the client's or the operator's proprietary source inside; the confidentiality breach costs the client.
- Evidence: "The designed variant that holds diagrams alone, for an outside reviewer who should not see code, is not built" (DEL-02, For the business); the layer-table row versus the binary (`docs/DESIGN.md:84` vs `docs/DESIGN.md:223`, `main.rs:45`-`65`); pack contents (`pack.rs:274`); the working-tree diff semantics (DEL-02.3, `docs/DESIGN.md:203`, `docs/DESIGN.md:213`-`222`).
- Warning signs visible today: the gap is recorded as Debt in DEL-02.1 while `docs/DESIGN.md:84` still documents the mode as part of the pack layer — the design document and the binary disagree on a security-relevant property.
- Confidence: high on the gap; the leak scenario is inferred.
- Severity: high.

### R-3 — The "byte-identical on any machine" promise is false whenever `--name` is not pinned, and the determinism gate pins it, so the flaw ships untested
- Topics: DEL-01 (For the business), DEL-01.3
- Chain of events:
  1. A downstream harness generates corpora without `--name`; the pin `--name sealmap` is a CI argument of this repository (`.github/workflows/ci.yml:29`), not a tool default or an enforcement.
  2. The codebase name becomes the canonicalised checkout directory (`crates/sealmap/src/main.rs:393`, `main.rs:419`-`424`) and "reaches the index and overview".
  3. The same commit generated in two differently named directories — two runners, two engineers, a re-cloned cache builder — produces different bytes, contradicting the promise the harness built its caching and diffing on ("results can be cached, diffed and compared in CI without noise").
  4. Constant name-derived diff noise either thrashes the cache or trains a normalisation step to ignore diffs; a genuine change is dismissed as name noise. In seal flows where no `Cargo.toml` names the package, the same ambient name perturbs stale comparisons — the special case in `stale --since` (reading the older tree under the current tree's name) exists precisely because of this.
- Evidence: the contract "no ambient data" (`crates/sealmap-model/src/lib.rs:33`-`34`) against the CLI behaviour (`main.rs:393`, `main.rs:419`-`424`); "two clones in differently named directories produce different bytes" (DEL-01.3, Tension); the determinism job compares two fresh generations in one job with the name pinned (`ci.yml:26`-`30`, `ci.yml:29`) — the single input that leaks ambient data is excluded from every determinism test.
- Warning signs visible today: the Tension is marked in DEL-01.3; the CI pin is the tell that the tool default is unsafe; the `stale --since` workaround shows the authors already hit this class of problem.
- Confidence: high on the mechanism; the incident chain is inferred.
- Severity: high.
